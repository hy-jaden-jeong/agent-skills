# 검증

만든 것을 spec에 비춰 세 방향에서 본다. 발견한 것을 보고하고, 고치는 것은 사용자가 정한 뒤에 한다.

만든 쪽은 자기 코드를 변호한다. subagent를 쓸 수 있으면 방향마다 새 subagent에게 맡긴다. 지시문에는 diff를 얻는 명령과 spec 경로를 준다. 만든 과정의 설명은 주지 않는다. subagent를 쓸 수 없으면 spec을 처음부터 다시 읽고 diff를 직접 본다. 그때는 만든 쪽이 검증했다는 것을 보고에 적는다.

## 준비

1. 무엇을 볼지 정한다. 기준점(commit, branch)부터 지금까지의 diff다. 기준점을 모르면 묻는다.
2. diff가 비어 있지 않은지 확인한다.
3. repo가 코드 쓰는 법을 문서로 정한 파일을 찾는다.
4. spec에 "회귀 기준"이 있으면 마지막 상태로 golden master를 한 번 더 굽고 견줘 검증 기록에 적는다.

## 방향 1: spec

spec의 줄을 인용해 보고한다.

- spec의 동작 중 빠졌거나 일부만 된 것
- spec에 없는데 diff에 들어간 동작
- 구현된 것처럼 보이지만 틀려 보이는 것
- spec의 결정 표와 다르게 만든 것

## 방향 2: 규칙

- repo가 문서로 정한 규칙을 어긴 곳. 규칙이 적힌 파일과 줄을 댄다.
- 도구(lint, formatter, type 검사)가 이미 잡는 것은 뺀다.
- 아래는 규칙이 없어도 보는 것이다. 어긴 것이 아니라 판단이 필요한 것으로 표시한다. repo의 규칙이 허락하면 뺀다.
  - 이름이 하는 일을 말해 주지 않는다
  - 같은 로직이 두 곳 이상에 있다
  - 같은 값 묶음이 여러 곳을 함께 다닌다(type이 될 것)
  - 한 가지를 바꾸려고 여러 파일을 흩어서 고쳤다
  - spec에 없는 필요를 위한 추상화나 옵션이 있다
  - 전달만 하는 함수나 class가 있다

## 방향 3: 깨뜨리기

spec의 의도를 깨는 경우를 찾아 실제로 돌려 본다.

- 발견마다 돌린 명령, 나온 결과, spec이 요구하는 결과를 적는다.
- golden master가 달라진 대상은 의도한 차이로 spec에 적혀 있지 않으면 발견이다.
- 돌려서 실패를 보인 발견만 남긴다. 돌려 보지 않은 걱정, 취향, 이름, 나중에야 문제가 될 위험은 뺀다. 뺀 수와 이유를 적는다.
- spec이 요구하지 않는 장면에서 본 실패는 발견에서 빼고 "범위 밖에서 본 것"으로 따로 알린다.
- 발견이 없는 것도 결과다.
- 재현 코드는 진짜 코드와 섞이지 않는 곳에 둔다.

## 보고

- 세 방향을 따로 보고한다. 섞거나 한 줄로 순위를 매기지 않는다. 한 방향이 다른 방향을 가리지 않게 한다.
- 방향마다 발견 수와 가장 심한 것 하나를 맨 위에 쓴다.
- spec의 동작마다 증명이 있는지 표로 보여 준다.
- 코드는 고치지 않고 보고한다. 사용자가 고칠 것을 정하면 그 발견을 구현 단계(같은 폴더의 `build.md`)의 차례로 고친다. spec이 틀렸던 것이면 spec을 먼저 고친다.
- spec의 글이 이미 정해진 결정에 뒤처진 것은 묻지 않고 고치고, 고쳤다고 보고에 적는다.

통과: 발견한 것을 보고했고, 사용자가 고칠 것을 정했고, 정한 것을 고쳤다. spec의 검증 기록에 결과를 적고 상태를 "검증 끝"으로 바꾼다.
