# spec 주도 개발

사용자와 인터뷰해 spec을 확정하고, 그 spec을 기준으로 만들고 검증한다.

끝났을 때 세 가지가 참이어야 한다. 사용자가 이 설계를 자기 말로 설명할 수 있다. 모든 결정에 사용자의 답이나 동의가 붙어 있다. spec의 동작마다 실제로 돌려 본 증명이 있다.

`references/`는 이 SKILL.md 옆 폴더다.

## 어디서 시작해 어디서 멈추나

| 요청 | 단계 |
| --- | --- |
| 한 module 안에서 끝나고 되돌리기 쉽다 | skill 없이 바로 한다 |
| 돌려 보면 답이 나오는 질문 하나다 | 버릴 prototype만 만든다(`references/design.md`의 "prototype") |
| 설계나 spec만 원한다 | 1 → 4 |
| 이미 세운 계획을 검토해 달라고 한다("grill me") | 1 → 3 → 4. 사용자의 계획이 shape다. 2단계는 건너뛴다 |
| 처음부터 끝까지 만든다 | 1 → 7 |
| 확정된 spec이 있다 | 5 → 7 |
| 구현이 끝났고 spec에 맞는지만 본다 | 7 |

module 경계를 넘거나, 상태의 owner가 바뀌거나, 되돌리기 비싼 변경(schema, 저장 형식, 공개 interface, 외부와 맺은 계약)은 1단계부터 한다.

## 단계

| # | 단계 | 읽을 파일 | 통과 조건 |
| --- | --- | --- | --- |
| 1 | 문제 맞추기 | `references/frame.md` | 사용자가 다시 쓴 문제에 동의했다 |
| 2 | 설계 | `references/design.md` | spec에 후보들, 고른 shape, 결정 목록이 있다 |
| 3 | 인터뷰 | `references/interview.md` | 물을 사용자 결정이 남지 않았다 |
| 4 | spec 확정 | `references/confirm.md` | 사용자가 확정한다고 말했다 |
| 5 | slice 나누기 | `references/slices.md` | 사용자가 나눈 slice에 동의했다 |
| 6 | 구현 | `references/build.md` | slice마다 증명이 spec에 적혀 있다 |
| 7 | 검증 | `references/verify.md` | 발견한 것을 보고했고, 고칠 것은 사용자가 정했다 |

- 단계에 들어갈 때 그 단계의 파일을 읽는다. 다음 단계의 파일은 통과 조건을 채운 뒤에 읽는다. 뒤 단계가 먼저 보이면 앞 단계를 서둘러 끝내게 된다.
- 통과 조건은 사용자의 말이나 spec에 적힌 내용으로 확인한다. 짐작으로 넘어가지 않는다.
- 4단계를 통과하기 전에는 구현을 시작하지 않는다.
- 뒤 단계에서 앞 단계가 틀렸다는 것이 드러나면 그 단계로 돌아간다. spec을 먼저 고치고 다시 내려온다.

## spec이 진행 상태다

1단계에서 spec 파일을 만들고, 무엇이든 정해지는 즉시 그 파일을 고친다. 형식은 `references/spec-format.md`에 있다. 이 파일은 단계와 상관없이 spec을 만들거나 고칠 때 읽는다.

- spec을 둘 곳은 이 skill이 정하지 않는다. 사용자가 정한 곳이나 repo의 관례를 따른다. 둘 다 없으면 1단계의 첫 질문에 넣어 묻는다.
- 대화가 끊겼다가 이어지면 spec을 읽고 상태를 보고 시작한다. "열림"인 결정이 있으면 3단계, slice가 남았으면 6단계다. 진행 상태를 spec 밖에 따로 적지 않는다.
- 단계를 넘어갈 때 대화가 길어졌으면 spec을 고쳐 둔 뒤 새 대화에서 spec을 읽고 이어 가자고 제안한다. 3단계에서 6단계로 갈 때는 같은 대화에서 잇는 편이 낫다. 구현이 결정의 이유를 그대로 쓴다.

## 사실과 결정

- 사실은 agent가 찾는다. 코드·문서·설정·실행 결과로 알 수 있는 것은 사용자에게 묻지 않는다. 넓게 읽어야 하고 subagent를 쓸 수 있으면 읽기 전용 subagent에게 맡긴다. 사실을 찾는 동안에도 그 사실과 상관없는 질문은 먼저 묻는다.
- 범위 밖의 문제를 찾으면 고치지 않는다. 사용자에게 알리고, 이번에 하지 않기로 하면 spec의 "하지 않을 것"에 적는다. 이 변경과 상관없이 원래 있던 문제가 범위 밖이다. 이 변경 때문에 새로 생기는 구멍은 설계 결정이다.
- 결정은 세 종류로 나눈다. 사용자에게는 첫 종류만 묻는다. 질문이 줄어야 사용자가 중요한 결정에 집중한다.

  | 종류 | 가르는 기준 | 하는 것 |
  | --- | --- | --- |
  | 사용자 결정 | 제품 방향이나 선호가 답을 정한다. 또는 되돌리기 비싸다 | 가르치고, 추천을 붙여 묻고, 답을 기다린다 |
  | agent 결정 | 되돌리기 쉽고 근거가 코드나 제약에 있다 | 정하고 근거 한 줄과 함께 spec에 적는다. 사용자는 목록을 보고 뒤집을 수 있다 |
  | 실험 결정 | 돌려 보면 답이 나온다 | 버릴 prototype을 돌려 본 결과로 정한다 |

"되돌리기 비싸다"는 나중에 바꾸려면 저장된 data를 옮겨야 하거나, 이 repo 밖의 caller를 고쳐야 하거나, 고객이 이미 겪은 동작(금액, 화면, 응답)을 바꿔야 한다는 뜻이다. 이 repo 안에서만 고치면 되는 것은 되돌리기 쉽다.

남은 결정을 모두 적고, 결정마다 종류와 먼저 정해져야 하는 결정을 적은 목록이 design tree다. spec의 결정 표에 적는다. 인터뷰는 이 목록을 따라간다.

## 질문 형식

사용자에게 묻는 모든 단계에서 쓴다. 지금 물을 수 있는 질문을 한 번에 모아 묻고 답을 기다린다. 이 묶음이 round다.

```
**Q1. <결정 제목>**
<이 결정이 왜 필요한지 한두 문장. 선택지와 선택지마다 치르는 값을 이 프로젝트의 장면으로.>
추천: <답> (<이유 한 줄>)
```

- "네" 한 마디가 추천을 받아들이는 뜻이 되게 쓴다. 사용자는 "1 네, 2는 B"처럼 답할 수 있다.
- round 끝에 그 사이 정한 agent 결정과 실험 결과를 "제가 정한 것" 목록으로 붙인다. 결정마다 근거를 한 줄 쓴다.
- 질문 수에 상한을 두지 않는다. 대신 사용자 결정이 아닌 것은 묻지 않는다.
- 사용자가 "나머지는 알아서 해"라고 하면 남은 사용자 결정과 그 뒤에 새로 생기는 사용자 결정을 추천대로 정하고 spec에 "추천대로"로 적는다. 그중 되돌리기 비싼 것은 spec을 확정받을 때 장면으로 보여 준다.

## 가르치는 법

질문할 때와 설계를 설명할 때 쓴다. 목표는 사용자가 그 결정을 스스로 내릴 만큼 이해하는 것이다.

- 사용자가 무엇을 아는지는 대화에서 읽는다. 이미 아는 것은 건너뛴다.
- 가장 작은 완전한 설명을 먼저 한다. 한두 문장이다. 일반 정의를 먼저 말하고 이 프로젝트의 경우로 잇는다. 사용자가 더 물으면 한 층 더 들어간다.
- 선택지의 값은 이 프로젝트의 장면으로 보여 준다. "유연하다" 대신 "결제 수단이 하나 늘 때 고칠 파일이 1개다"로 쓴다.
- 개념마다 이름을 하나만 쓴다. 사용자의 말이 spec의 용어와 어긋나면 바로 짚고, 맞춘 뜻을 spec의 용어 절에 적는다.
- 구조를 견줘야 이해되는 내용은 그림으로 보여 준다. 질문 round에서는 그림 없이 답하기 어려울 때만 그리고, 4단계에서 설계를 설명할 때는 꼭 그린다. 그림 한 장에 개념 하나를 담는다.
- 그림을 그리는 skill이 설치돼 있으면 그 skill을 쓰고, 없으면 Mermaid로 그린다. Mermaid 그림은 spec 본문에 넣는다. 그림 파일은 spec 옆에 둔다. 사용자나 다른 규칙이 정한 곳이 있으면 거기에 둔다.
