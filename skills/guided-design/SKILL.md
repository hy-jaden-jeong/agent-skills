# 함께 하는 설계

설계 하나를 다섯 단계로 끝낸다. 문제 맞추기 → 후보 설계 → 결정 round → 확정 → 문서 마무리.

끝났을 때 두 가지가 참이어야 한다. 사용자가 이 설계를 자기 말로 설명할 수 있다. 모든 결정에 사용자의 답이나 동의가 붙어 있다.

`<skills 폴더>`는 skill 폴더들이 나란히 설치된 곳이다(`~/.claude/skills`, `~/.agents/skills`). `references/`는 이 SKILL.md 옆 폴더다.

## 이 skill을 쓸 일인가

| 일 | 하는 것 |
| --- | --- |
| 한 module 안에서 끝나고 되돌리기 쉽다 | skill 없이 바로 한다 |
| 돌려 보면 답이 나오는 질문 하나다(layout, 속도, 어느 방법이 되는지) | 버릴 prototype만 만들어 답을 낸다 |
| module 경계를 넘는다, 상태의 owner가 바뀐다, 되돌리기 비싸다(schema, 저장 형식, 공개 interface, 외부와 맺은 계약) | 이 skill을 끝까지 따른다 |

## 사실과 결정

- 사실은 agent가 찾는다. 코드·문서·설정·실행 결과로 알 수 있는 것은 사용자에게 묻지 않는다. 넓게 읽어야 하면 읽기 전용 subagent에게 맡기고, 그 사실이 필요 없는 질문은 기다리지 않고 먼저 묻는다.
- 결정은 세 종류로 나눈다. 사용자에게는 첫 종류만 묻는다. 질문이 줄어야 사용자가 중요한 결정에 집중한다.

  | 종류 | 가르는 기준 | 하는 것 |
  | --- | --- | --- |
  | 사용자 결정 | 제품 방향이나 선호가 답을 정한다. 또는 되돌리기 비싸다 | 가르치고, 추천을 붙여 묻고, 답을 기다린다 |
  | agent 결정 | 되돌리기 쉽고 근거가 코드나 제약에 있다 | 정하고 근거 한 줄과 함께 기록한다. 사용자는 목록을 보고 뒤집을 수 있다 |
  | 실험 결정 | 돌려 보면 답이 나온다 | 버릴 prototype을 돌려 본 결과로 정한다 |

## 설계 추론을 맡는 모델

후보 설계(2단계)는 쓸 수 있는 가장 강한 모델이 한다. 첫 설계의 질이 뒤 단계 전부를 정하기 때문이다.

- 세션 모델이 Fable이면 직접 한다. 맡기지 않는다.
- Claude Code에서 세션 모델이 Fable이 아니면 2단계만 `fable-solver` 에이전트에게 맡긴다. 그 에이전트가 없으면 Agent 도구를 `model: fable`, `effort: high`로 부른다. 지시문은 `references/brief.md`를 따른다. 사용자와의 대화(1·3·4단계)는 세션이 계속 맡는다. subagent는 사용자에게 물을 수 없다.
- Fable을 부를 수 없는 agent에서는 세션 모델이 그대로 한다.

## 설계 문서가 진행 상태다

1단계에서 설계 문서 파일을 만들고, 무엇이든 정해지는 즉시 그 파일을 고친다. 형식은 `references/design-doc.md`에 있다.

- 위치는 repo가 설계 문서를 두는 곳이다. 그런 곳이 없으면 `docs/design/<slug>.md`에 둔다. 사용자가 정한 곳이 있으면 거기에 둔다.
- 대화가 끊겼다가 이어지면 문서를 읽고 "열림" 상태인 결정부터 다시 시작한다. 진행 상태를 문서 밖에 따로 적지 않는다.

## 가르치는 법

3단계와 4단계에서 쓴다. 목표는 사용자가 그 결정을 스스로 내릴 만큼만 이해하는 것이다.

- 사용자가 무엇을 아는지는 대화에서 읽는다. 이미 아는 것은 건너뛴다.
- 가장 작은 완전한 설명을 먼저 한다. 한두 문장이다. 일반 정의를 먼저 말하고 이 프로젝트의 경우로 잇는다. 사용자가 더 물으면 한 층 더 들어간다.
- 선택지의 값은 이 프로젝트의 장면으로 보여 준다. "유연하다" 대신 "결제 수단이 하나 늘 때 고칠 파일이 1개다"로 쓴다.
- 개념마다 이름을 하나만 쓴다. 사용자의 말이 문서의 용어와 어긋나면 바로 짚고, 맞춘 뜻을 문서의 용어 절에 적는다.
- 구조를 견줘야 이해되는 내용은 그림으로 보여 준다. `<skills 폴더>/diagram-slides`가 있으면 그 skill로 그리고, 없으면 Mermaid로 그린다. 부품이 3개 이상이면 한 장에 다 넣지 않고 하나씩 더해 가며 그린다.

## 1. 문제 맞추기

1. 사용자의 목표와 풀려는 문제를 내 말로 다시 쓴다. 사용자가 말한 해법을 옮겨 적지 않고, 그 해법이 풀려는 문제를 쓴다.
2. 이 변경이 닿는 system을 전부 따라가며 읽는다. 지금 구조, 상태를 가진 곳, 호출하는 쪽을 적는다.
3. 전제를 묻는다. 목표, 하지 않을 것(non-goal), 제약, 끝났는지 확인하는 방법이다. 형식은 3단계의 질문 형식을 따른다.

완료: 사용자가 다시 쓴 문제에 동의했다. 문서에 문제, 목표, non-goal, 제약, 확인 방법이 적혀 있다.

## 2. 후보 설계

1. 서로 다른 shape를 2개 이상 만든다. 크거나 의견이 갈리는 설계는 3개를 만든다. 후보마다 다른 제약을 걸면 달라진다. 예: interface를 가장 작게, 가장 흔한 caller가 가장 쉽게, 나중에 바꾸기 가장 쉽게.
2. 후보마다 네 가지를 적는다. type·interface·module 경계(또는 data model), caller가 쓰는 예 하나, 안에 숨기는 것, 치르는 값.
3. 하나를 고른다. 기준은 세 가지다. 상태마다 owner가 하나다. 일마다 방법이 하나다. caller가 알아야 할 것이 가장 적다. 1단계의 제약을 어기는 후보는 뺀다.
4. 진 후보에서 가져올 부분이 있으면 고른 shape에 직접 녹인다. 후보들이 한 shape로 모이면 그 shape가 답이다. 후보들이 크게 갈리면 1단계가 모자랐다는 뜻이다. 1단계로 돌아간다.
5. 고른 shape에 남은 결정을 모두 적고 세 종류로 나눈다. 결정마다 먼저 정해져야 하는 결정을 적는다. 이것이 design tree다.

완료: 문서에 후보들, 고른 shape와 이유, 버린 후보와 이유, 종류를 나눈 결정 목록이 있다.

## 3. 결정 round

frontier는 먼저 정해져야 하는 결정이 모두 정해져서 지금 물을 수 있는 사용자 결정 전부다. round마다 frontier 전체를 한 번에 묻고 답을 기다린다. 다른 질문의 답에 달린 질문은 다음 round로 넘긴다.

질문은 이 형식으로 쓴다.

```
**Q1. <결정 제목>**
<이 결정이 왜 필요한지 한두 문장. 선택지와 선택지마다 치르는 값을 이 프로젝트의 장면으로.>
추천: <답> (<이유 한 줄>)
```

- "네" 한 마디가 추천을 받아들이는 뜻이 되게 쓴다. 사용자는 "1 네, 2는 B"처럼 답할 수 있다.
- round 끝에 그 사이 정한 agent 결정과 실험 결과를 "제가 정한 것" 목록으로 붙인다. 결정마다 근거를 한 줄 쓴다.
- 답을 받으면 문서의 결정 목록을 고치고 frontier를 다시 계산한다.
- 답이 shape를 바꾸면 2단계로 돌아가 shape를 고친다. `fable-solver`에게 맡겼다면 같은 에이전트에게 이어서 보낸다.
- 사용자가 "나머지는 알아서 해"라고 하면 남은 사용자 결정을 추천대로 정하고, 4단계 목록에 "추천대로 정함"으로 표시한다.

완료: frontier가 비었다. 모든 사용자 결정에 답이 있다.

## 4. 확정

1. 설계 전체를 한 번 가르친다. 한 문단으로 먼저 말하고, 그림으로 보여 주고, 결정 목록으로 끝낸다.
2. 되돌리기 비싼 결정마다 장면 하나로 결과를 확인한다. "이 결정이면 <장면>에서 <결과>가 됩니다. 원하는 결과가 맞나요?" 사용자가 뜻을 다르게 알고 동의한 결정을 여기서 잡는다.
3. 결정 목록을 번호(D1, D2, …)와 함께 보여 준다. 사용자가 답한 것, agent가 정한 것, 추천대로 정한 것을 구분한다.
4. 사용자가 일부를 고치면 그 결정과 거기에 달린 결정만 다시 묻는다.

완료: 사용자가 확정한다고 말했다. 그 전에는 구현을 시작하지 않는다.

## 5. 문서 마무리

1. 문서 상태를 "확정"과 날짜로 바꾼다.
2. 구현 순서를 쓴다. 확인할 수 있는 작은 단위로 나누고, 단위마다 동작을 증명하는 방법을 적는다. test 통과만으로는 증명이 아니다. 구현 순서는 설계가 확정된 뒤에만 쓴다.
3. 문서 경로와 결정 수를 알리고 끝낸다. 구현은 사용자가 시작하라고 할 때 한다.
