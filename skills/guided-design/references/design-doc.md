# 설계 문서 형식

설계 하나에 파일 하나다. 1단계에서 만들고, 정해지는 즉시 고친다. 쓸 내용이 있는 절만 둔다.

```md
# <설계 제목>

상태: 초안 | 확정 (YYYY-MM-DD)

## 문제

<지금 무엇이 안 되는지, 누구에게 문제인지. 사용자의 관점에서 쓴다.>

## 목표와 하지 않을 것

- 목표: <이 설계가 끝나면 참이 되는 것>
- 하지 않을 것: <범위 밖으로 정한 것과 이유>

## 제약

<어길 수 없는 것. 코드에 드러나지 않는 제약(규정, 외부 계약, 응답 시간)을 꼭 적는다.>

## 끝났는지 확인하는 방법

<통과와 실패가 갈리는 확인. "더 좋아진다"는 확인이 아니다.>

## 용어

- **<용어>**: <한 줄 뜻. 구현 내용은 쓰지 않는다.>

## 설계

<고른 shape. 한 문단 요약, 그림(Mermaid), type·interface·module 경계 또는 data model, 주요 흐름.>

## 결정

| # | 결정 | 답 | 정한 쪽 | 이유와 버린 대안 | 상태 |
| --- | --- | --- | --- | --- | --- |
| D1 | <무엇을 정하는가> | <답> | 사용자 / agent / 실험 / 추천대로 | <한두 문장> | 열림 / 정해짐 |

## 버린 후보

- **<후보 이름>**: <shape 한 줄>. 버린 이유: <한 줄>

## 구현 순서

<설계가 확정된 뒤에만 쓴다. 단위마다 하는 일과 동작을 증명하는 방법.>
```

## 쓰는 법

- 결정의 "이유와 버린 대안"은 한두 문장이다. 나중에 읽는 사람이 "왜 이렇게 했지"를 묻지 않게 하는 것이 목적이다.
- "정한 쪽"이 실험이면 돌린 명령과 본 결과를 이유에 적는다.
- 파일 경로와 코드 조각은 결정을 글보다 정확히 담을 때만 넣는다(schema, type, 상태 전이). 금방 낡는 내용은 넣지 않는다.
- 용어 절에는 뜻만 적는다. 설계 결정은 결정 표에 적는다.
