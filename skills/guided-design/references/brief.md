# 후보 설계를 맡기는 지시문

세션 모델이 Fable이 아닐 때 2단계를 `fable-solver`에게 맡기며 쓴다. 맡기기 전에 1단계가 끝나 있어야 한다. 설계 문서에 문제, 목표, non-goal, 제약, 확인 방법이 적혀 있다.

## 지시문

아래 칸을 채워 보낸다. 문제와 제약은 지시문에 옮겨 적지 않고 설계 문서를 읽게 한다. 같은 내용을 두 곳에 두면 어긋난다.

```md
# 설계: <제목>

## 원하는 결과
<설계 문서 경로>의 문제를 푸는 설계다. 서로 다른 shape를 <2 또는 3>개 만들고 하나를 추천한다.
추천한 shape에 남은 결정을 모두 찾아 세 종류로 나눈다.
- 사용자 결정: 제품 방향이나 선호가 답을 정한다. 또는 되돌리기 비싸다.
- agent 결정: 되돌리기 쉽고 근거가 코드나 제약에 있다. 네가 정한다.
- 실험 결정: 돌려 보면 답이 나온다. 버릴 prototype을 돌려 정한다.

## 읽을 곳
- 설계 문서: <경로> (문제, 목표, non-goal, 제약, 확인 방법)
- 코드: <이 변경이 닿는 폴더와 파일>
- <그 밖의 문서, 기록>

## 이미 정해진 것
<사용자가 정한 전제와 그 이유. 이미 버린 접근이 있으면 버린 이유.>

## 해도 되는 것
- 위 경로와 그 주변 코드를 읽는다.
- 설계 문서의 "설계", "결정", "버린 후보" 절을 직접 쓴다.
- <scratch 경로> 안에서 버릴 prototype을 만들고 돌린다.

## 돌려줄 것
설계 문서에 쓴다.
- 후보마다: type·interface·module 경계(또는 data model), caller가 쓰는 예 하나, 안에 숨기는 것, 치르는 값
- 추천한 shape와 이유, 버린 후보와 이유
- 결정 표: 결정마다 종류, 먼저 정해져야 하는 결정, 네가 정한 답과 근거

보고에는 이것만 쓴다.
- 추천한 shape를 한 문단으로
- 사용자 결정 목록: 결정마다 선택지, 선택지마다 치르는 값(이 프로젝트의 장면으로), 추천과 이유
- 확인하지 못한 것
```

## 쓰는 법

- 원하는 결과를 쓰고 단계는 쓰지 않는다. 접근법은 맡은 모델이 정한다.
- 애매한 문제는 애매한 채로 넘긴다. 먼저 좁혀서 넘기면 더 나은 shape를 못 찾는다.
- 해도 되는 일은 이름을 적어 허락한다. "조심해라" 같은 일반 문장은 넣지 않는다. 그런 문장이 쌓이면 필요 없는 승인을 구하며 멈춘다.
- 생각을 줄이라는 문장과 token 예산은 넣지 않는다. 깊이는 effort로 정한다.
- 사용자에게 물을 것은 묻지 못한다. 그래서 사용자 결정은 목록으로 돌려받는다.

## 받은 뒤

- 설계 문서를 직접 읽는다. 보고 요약만 믿지 않는다.
- 추천한 shape가 기대는 사실(지금 코드의 구조, 호출하는 쪽, 제약)을 코드에서 직접 확인한다. 틀린 사실 위에 선 shape는 3단계로 넘기지 않는다.
- 3단계에서 사용자의 답이 shape를 바꾸면 같은 에이전트에게 이어서 보낸다. 새로 부르면 맥락을 다시 모은다.
