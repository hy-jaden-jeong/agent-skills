# debate with Fable

메인은 처음부터 끝까지 작업 모델이다. 사용자와 이야기하고, 구현하고, 검증하고, 마지막 판단을 내린다. 판단 모델은 무거운 순간에만 subagent로 불러 토론한다. 판단 모델은 단가가 높아서, 판단이 결과를 가르는 곳에만 쓴다.

## 역할

| 역할 | 맡는 일 | Claude Code |
| --- | --- | --- |
| 작업 모델 | 메인 세션. 사용자와 대화, 구현, 검증, 견주고 고르기 | Opus 5.5 |
| 판단 모델 | 토론 상대. subagent로만 부른다 | Fable 5.2: `fable-solver` 에이전트, 없으면 Agent 도구에 `model: fable`, `effort: high` |
| 싼 모델 | 그리기, 정해진 대로 고치기, 단순 검색 | Sonnet 5.5: `sonnet-worker` 에이전트 |

- 세션 모델을 판단 모델로 바꾸자고 하지 않는다. 판단 모델을 메인으로 두고 일을 나눠 주는 구성은 비용만 늘었다.
- subagent는 사용자에게 묻지 못한다. 사용자에게 묻는 것은 언제나 메인이다. 묻는 법은 `grill-me` skill을 따른다.
- 판단 모델을 부를 수 없는 agent에서는 메인이 혼자 서로 다른 안을 두 개 만들어 견준다. 아래 "토론하는 법"의 3~5번을 그대로 따른다.

## 언제 무엇을

| 순간 | 하는 것 |
| --- | --- |
| 설계. 시스템, data model, pipeline, interface의 모양을 정한다 | 토론 |
| 접근법부터 찾아야 하는 문제 | 토론 |
| 되돌리기 비싼 결정을 고른다(저장된 data를 옮겨야 바뀐다, 다른 사람이나 system이 기대고 있다, 고객이 이미 겪는다) | 토론 |
| 같은 문제를 두 번 고쳤는데 안 풀린다 | 토론. 두 번의 시도가 함께 기댄 전제를 문제 글에 적는다 |
| 한 module 안의 수정, 정해진 대로 고치기, 사실 찾기, 이름 고르기 | 토론하지 않는다. 고르는 이름을 밖에서 이미 부르고 있으면 되돌리기 비싼 결정이다 |

- 사용자가 "Fable과 토론해"라고 하면 위 표와 상관없이 토론한다.
- 같은 문제를 두 번 고쳤는데 안 풀리면 effort를 올리지 않고 바로 토론한다. effort를 올리는 것은 틀리지는 않았지만 결과가 얕을 때다.
- spec을 남기는 설계(코드가 있는 일)는 `spec-driven` skill을 먼저 부른다. 그 skill의 설계 단계가 이 skill의 "토론하는 법"을 쓴다. 사용자와 문제를 먼저 맞추고 나서 토론하기 위해서다. spec 없이 정할 것 하나를 두고 토론할 때는 이 skill을 바로 쓴다.

## 토론하는 법

1. **문제 글을 쓴다.** 둘이 같은 글을 받는다. 메인의 안은 넣지 않는다. 서로의 첫 생각에 기대지 않아야 한쪽이 놓친 것을 다른 쪽이 잡는다. 이미 해 본 것(버린 접근과 그 결과, 함께 기댄 전제)은 사실이라 적는다. 메인이 새로 세운 가설은 적지 않는다.

   ```md
   # <제목>

   ## 원하는 결과
   <무엇을 정해야 하는지. 안을 하나(크면 둘) 내고 추천해 달라고 쓴다.>

   ## 읽을 곳
   <파일, 폴더, 문서, spec 경로>

   ## 이미 정해진 것
   <사용자가 정한 것과 그 이유. 어길 수 없는 제약. 이미 버린 접근과 버린 이유.>

   ## 해도 되는 것
   - 위 경로와 그 주변을 읽는다.
   - <scratch 경로> 안에서 버릴 prototype을 만들고 돌린다.

   ## 돌려줄 것
   - 안: 모양(type, interface, 경계, 흐름)과 caller가 쓰는 예 하나
   - 근거: 기대는 사실과 그 출처(파일:줄)
   - 치르는 값과 버린 대안
   - 확인하지 못한 것
   ```

   - 원하는 결과를 쓰고 단계는 쓰지 않는다. 접근법은 판단 모델이 정한다.
   - 애매한 문제는 애매한 채로 넘긴다. 먼저 좁혀서 넘기면 더 나은 안을 못 찾는다.
   - 해도 되는 일은 이름을 적어 허락한다. "조심해라" 같은 일반 문장은 넣지 않는다.
   - 생각을 줄이라는 문장과 token 예산은 넣지 않는다.
   - 판단 모델은 파일을 고치지 않는다. 결과를 spec이나 문서에 쓰는 것은 메인이다.

2. **판단 모델을 띄운다.** background로 띄우고 기다리지 않는다.
3. **메인도 자기 안을 쓴다.** 같은 문제 글을 보고, 판단 모델의 답을 보기 전에 끝낸다. 형식은 "돌려줄 것"과 같다.
4. **견준다.**
   - 두 안이 기대는 사실을 코드와 문서에서 직접 확인한다. 틀린 사실 위에 선 안은 뺀다.
   - 고르는 기준은 셋이다. 상태마다 owner가 하나다. 일마다 방법이 하나다. caller가 알아야 할 것이 가장 적다. 어길 수 없는 제약을 어기는 안은 뺀다.
   - 두 안이 같은 곳으로 모이면 그것이 답이다.
   - 갈리면 갈린 곳을 하나로 좁혀 같은 판단 모델에게 한 번만 더 묻는다(이어서 보내기). 이때는 메인의 안과 이유를 보여 줘도 된다. 새로 부르면 맥락을 처음부터 다시 모은다.
   - 그래도 갈리면 메인이 고른다. 갈린 곳이 방향이나 선호가 정할 결정이면 사용자에게 묻는다.
   - 진 안에서 가져올 부분이 있으면 고른 안에 직접 녹인다. 붙여 넣지 않는다.
5. **결론을 보여 준다.** 결론 하나와 이유 한두 줄을 쓴다. 토론 과정과 진 안은 사용자가 물을 때만 보여 준다. 사용자가 정할 결정이 남았으면 `grill-me`의 질문 형식으로 묻는다.

## 통째로 맡길 때

판단 모델이 한 조각을 끝까지 하는 것이 맞는 일도 있다. 몇 시간 이어지는 작업, 여러 단계의 조사, 분석을 완성된 문서까지 끌고 가는 일이다. 이때는 토론하지 않고 판단 모델 subagent에게 맡긴다. 지시문은 위 문제 글과 같은 칸을 쓰고, "돌려줄 것"에 완성할 결과물을 적는다. 받은 결과는 메인이 직접 확인한다.
