# 문제 맞추기 (spec으로 남길 때)

설계를 시작하기 전에 풀 문제가 같은지 확인한다. 틀린 문제 위에 세운 설계는 뒤의 일이 전부 버려진다.

1. 사용자의 목표와 풀려는 문제를 내 말로 다시 쓴다. 사용자가 말한 해법을 옮겨 적지 않고, 그 해법이 풀려는 문제를 쓴다. 문제를 코드로 알 수 없으면 가장 그럴듯한 문제를 짐작해 쓰고 round의 첫 질문으로 확인받는다.
2. 이 변경이 닿는 system을 전부 따라가며 읽는다. 지금 구조, 상태를 가진 곳, 호출하는 쪽, 이미 있는 용어와 결정 기록을 본다.
3. spec 파일을 만들고 문제와 지금 구조를 적는다. 둘 곳이 정해지지 않았으면 4번의 round에 넣어 묻는다. 답을 받은 뒤 만들고, 그 사이 정해진 것을 옮겨 적는다.
4. 전제를 round로 묻는다. 형식은 SKILL.md의 "질문 형식"을 따른다. 전제는 네 가지다.
   - 목표: 이 일이 끝나면 참이 되는 것
   - 하지 않을 것: 범위 밖으로 둘 것
   - 제약: 어길 수 없는 것. 코드에 드러나지 않는 제약(규정, 외부 계약, 응답 시간, 일정)을 꼭 묻는다
   - 끝났는지 확인하는 방법: 통과와 실패가 갈리는 확인. "더 좋아진다"는 확인이 아니다
5. 전제는 무엇을 풀지를 정한다. 목표와 하지 않을 것에는 밖에서 보이는 범위만 쓴다. 어떻게 풀지는 설계와 round에서 정한다.
6. 코드에서 답을 찾은 전제는 묻지 않는다. round 끝에 "확인한 것"으로 근거(파일과 줄)와 함께 보여 준다.

사용자가 이미 세운 계획을 들고 왔으면 그 계획을 다시 쓰고, 계획이 풀려는 문제를 따로 쓴다. 계획대로 하면 문제가 풀리지 않는 곳이 있으면 이 round에서 짚는다. 계획의 나머지 세부는 인터뷰에서 다룬다.

통과: 사용자가 다시 쓴 문제에 동의했다. spec에 문제, 목표, 하지 않을 것, 제약, 확인 방법이 적혀 있다.
