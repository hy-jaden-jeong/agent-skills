# 모션그래픽 만드는 법

같은 그림 위에서 상태가 시간 순서로 바뀌는 내용을 설명할 때 읽는다. 모션그래픽은 브라우저에서 재생하는 HTML 한 파일이다. 재생·멈춤·단계 이동이 되고, 단계마다 자막이 그림 아래에 나온다. `<스킬 폴더>`는 이 SKILL.md가 있는 폴더다. 장표는 `diagram-slides` skill이 맡는다. 두 skill은 같은 skills 폴더에 나란히 설치한다.

## 장표와 모션그래픽 중 고르기

기본은 장표다. 순서나 시점이 핵심이라도 한 장에 다 보이면 `diagram-slides` skill로 장표를 그린다. 요청과 응답이 오가는 순서는 `slide-sequence.html`, 일이 일어난 차례는 `slide-timeline.html`, 언제 시작해 얼마나 걸리는지는 `slide-timebar.html`이 한 장에 보여 준다(`diagram-slides` "모양 고르기").

아래 넷을 모두 만족할 때만 모션그래픽으로 만든다. 사용자에게 묻지 않고 고른다.

1. 그림(상자와 화살표)은 그대로이고 상자의 상태만 바뀐다.
2. 상태가 바뀌는 단계가 4개 이상이다. 3개 이하면 장표 한 장에 번호로 적는다.
3. 순서나 시점이 설명의 핵심이다. "A가 끝나야 B가 출발한다", "어디서 갈라지고 어디서 다시 만나나", "지금 구조와 바꾼 구조가 같은 날 어떻게 다르게 도나" 같은 질문이 여기 든다.
4. 한 장의 장표로는 안 보인다. 갈래가 있는 그림 위에서 데이터 한 건이 어디를 먼저 거치고 어디서 기다렸다가 넘어가는지(두 곳에 함께 쓰고, 한쪽이 확인된 뒤에만 다음 상자가 출발하는 것), 같은 그림 위의 두 경우를 견주는 것(새 데이터가 있는 날과 없는 날)이 여기 든다. sequence·timeline·timebar 한 장으로 그 차례가 다 보이면 장표다.

| 설명할 것 | 고를 것 |
| --- | --- |
| 갈래가 있는 그림 위에서 데이터 한 건·실행 한 번이 평소에 거쳐 가는 차례(어디서 갈라지고, 무엇이 끝나야 다음이 출발하나) | 모션그래픽 |
| 같은 그림 위의 두 정상 경로 견주기(새 데이터가 있는 날과 없는 날), 지금 구조와 바꾼 구조를 같은 날로 견주기, 같은 요청을 두 방식으로 풀어 견주기(RDB가 row를 전부 읽는 검색과 검색엔진이 inverted index로 찾는 검색) | 모션그래픽 (시나리오로 나눈다) |
| 실패가 퍼지는 범위, 정상인 경우와 실패한 경우를 견주기 | 넣을지 판단한다(아래 "정상 흐름이 기본이다"). 넣으면 정상 흐름 뒤의 시나리오로 둔다 |
| 요청이 여러 시스템을 거치는 순서(누가 누구에게) | 장표 (`slide-sequence.html`) |
| job이 도는 차례 | 장표 (`slide-timeline.html`). 걸리는 시간·겹침이 중요하면 `slide-timebar.html` |
| 구조, 구성요소가 사는 곳, 용어 구분, 개념끼리 대응 | 장표 |
| 데이터 한 건의 모양이 층마다 바뀌는 모습(칸 이름·값) | 장표 (`slide-compare.html`). 재생기는 상자 안의 값을 보여 주지 못한다 |

사용자가 장표나 모션그래픽을 콕 집어 청하면 기준과 상관없이 그대로 만든다. 이때도 시나리오는 아래 "정상 흐름이 기본이다"를 따른다.

장표로 설명한 뒤 "그래픽으로도", "움직이는 걸로" 같은 요청이 오면 무엇을 움직일지는 사용자가 처음 던진 질문이 정한다.

- 질문의 핵심부터 시나리오로 만든다. "왜 따로 필요한가"를 물었으면 그 답(기존 방식과 새 방식이 같은 요청을 어떻게 다르게 푸는지)이 첫 모션그래픽이다. 내부 구조나 동작 같은 뒷 장표 내용은 그다음이다.
- 장표마다 그림이 달라 한 파일에 담을 수 없으면 질문의 핵심을 담은 파일을 먼저 만들고, 나머지는 따로 만든다.
- skill을 부를 때 넘기는 인자에도 질문의 핵심을 먼저 적는다. 인자에서 빠진 것은 만들 때도 빠진다.

## 정상 흐름이 기본이다

모션그래픽은 "평소에 어떻게 도는가"를 가르치는 데 쓴다. 처음 배우는 사람은 정상 흐름을 먼저 알아야 하고, 실패한 경우는 정상 흐름을 안 뒤에야 뜻이 통한다.

- 시나리오는 정상 흐름 하나가 기본이다. 여럿으로 나눌 때도 정상 경로끼리 나눈다(새 데이터가 있는 날과 없는 날, 경로 A와 경로 B, 지금 구조와 바꾼 구조).
- 실패·정지·장애 시나리오는 넣을지 판단해서 정한다. 사용자에게 묻지 않고 정하고, 넣었으면 채팅에 넣은 까닭을 한 줄로 쓴다.
  - 넣는 쪽: 사용자가 실패한 경우를 물었다("실패하면 어떻게 되나"). 배우는 목적이 운영·장애 대응이다. 그 구조가 실패를 다루려고 있는 것이라 정상 흐름만으로는 왜 그렇게 생겼는지 설명되지 않는다(retry queue, dead letter queue, 앞이 확인된 뒤에만 다음으로 보내는 순서).
  - 빼는 쪽: 처음 보는 흐름을 익히는 단계다. 실패한 경우가 자료의 이슈·위험 절에만 나온다. 정상 흐름과 견줘 새로 알게 되는 것이 없다.
  - 넣을 때는 정상 흐름 시나리오를 맨 앞에 두고, 실패 시나리오는 한두 개로 줄인다.
- 자료에 이슈·위험·미결 사항이 적혀 있어도 시나리오로 옮기지 않는다. 그런 내용은 시스템이 도는 방식이 아니라 그 문서를 쓴 날의 사정이다. 알려야 하면 채팅에 한 줄로 쓰고 출처를 단다.
- 자료가 어느 날의 상태를 적은 것(snapshot)이면 그 상태를 "지금 이렇게 돈다"로 그리지 않는다. 그 뒤로 바뀌었을 수 있다.
- 정상 흐름 시나리오에는 `idle`·`run`·`wait`·`ok`·`skip`만 쓴다. `fail`·`blocked`·`warn`은 실패 시나리오에서만 쓰고, 정상 흐름의 `result`에도 `bad`·`warn`을 쓰지 않는다. 굽는 스크립트는 이 상태들이 든 시나리오를 구운 뒤 알려 준다.

## 무엇을 만드나

- 모션그래픽 HTML 한 파일. 음성은 넣지 않는다. 자막이 설명을 맡는다.
- 요약 장표 1장(PNG). 모션그래픽의 마지막 모습이나 핵심 단계를 `diagram-slides` skill의 "모양 고르기" 표에서 맞는 모양으로 그린다(데이터가 거쳐 가는 길은 `slide-flow.html`, 도는 시각은 `slide-timebar.html` 등). 설명 패널에는 핵심·용어·읽는 법을 적는다. 모션그래픽은 다시 열어 재생해야 보이지만 장표는 PNG로 남아 복습 자료와 퀴즈 근거가 된다. onboarding 단계가 아닌 평소 설명에서는 요약 장표를 생략해도 된다.

## spec 쓰기

내용은 JSON 파일(spec)에만 쓴다. 재생기(`assets/motion.html`)는 고치지 않는다. 견본은 `<스킬 폴더>/assets/motion-spec.json`이다.

```json
{
  "title": "탭 제목 두세 단어",
  "heading": "무엇이 움직이는 모습인지 한 문장",
  "lead": "무엇을 예로 들었는지. 지어낸 시각·값이면 (가상)",
  "source": "근거: path:line, 문서",
  "state_labels": { "skip": "새 데이터 없어 건너뜀" },
  "nodes": [
    { "id": "ingest", "sub": "원본 수집", "col": 0, "row": 0,
      "desc": "상자를 눌렀을 때 나오는 한 문장",
      "facts": [["기다리는 것", "없음"], ["compute", "serverless"]] }
  ],
  "edges": [
    { "from": "ingest", "to": "build" },
    { "from": "build", "to": "archive", "from_side": "right", "to_side": "top", "via": [1, 1.5], "tag": "copy" }
  ],
  "groups": [{ "label": "묶음 이름", "nodes": "*" }],
  "scenarios": [
    { "name": "① 새 데이터가 들어온 날",
      "steps": [
        { "t": "02:00", "set": { "ingest": "run" }, "text": "자막 한두 문장" },
        { "t": "02:10", "set": { "ingest": "ok", "build": ["run", "집계 중"] }, "text": "…" }
      ],
      "result": [["job 결과", "성공", "good"], ["보관", "1건"]] }
  ]
}
```

- `nodes`: 상자. `id`는 코드에 나오는 실제 이름을 쓴다(20자까지). `sub`는 한 줄 설명(26자까지). 자리는 격자로 정한다. `col`은 왼쪽에서, `row`는 위에서 몇 번째인지이고 0부터 센다. 1.6 같은 소수로 사이에 둘 수 있다. 흐름은 위에서 아래로, 갈래는 왼쪽·오른쪽으로 나눈다. 상자는 12개까지다.
- `edges`: 화살표. 기본은 위 상자의 아래에서 아래 상자의 위로 잇는다. 옆에서 나가거나 들어가게 하려면 `from_side`·`to_side`에 `top`·`bottom`·`left`·`right`를 쓴다. 다른 상자를 지나가면 `via: [col, row]`로 지나갈 점을 준다. `tag`는 시나리오에서 이 화살표를 가리킬 이름이다.
- `groups`: 점선 묶음과 이름. `"nodes": "*"`는 전체다. 시나리오 안에 `groups`를 쓰면 그 시나리오에서만 다르게 묶는다(예: 지금은 job 둘, 바꾸면 job 하나).
- `scenarios`: 5개까지. 기본은 정상 흐름 하나이고, 견줄 경우가 있으면 하나씩 더한다("정상 흐름이 기본이다"). 단계는 시나리오마다 2~12개다.
  - `steps[].set`: 이 단계에서 바뀌는 상자만 적는다. 적지 않은 상자는 앞 단계 상태 그대로다. 값은 상태 이름이고, `["run", "집계 중"]`처럼 쓰면 상자 아래 글자를 바꾼다. 한 상태의 글자를 주제에 맞게 통째로 바꾸려면 맨 위 `state_labels`에 적는다.
  - `steps[].text`: 자막. 무엇이 왜 바뀌는지 한두 문장, 170자까지. 자막만 읽어도 그 단계가 이해되어야 한다.
  - `steps[].t`: 왼쪽 위에 크게 보이는 시각이나 단계 이름(8자까지). 지어낸 시각이면 `lead`에 (가상)이라고 적는다.
  - `result`: 마지막 단계에서 보이는 결과 줄(6줄까지). 세 번째 값은 `good`(✓)·`warn`(!, 빨강)·`bad`(빨강)이고 생략할 수 있다.
  - `loose`: 이 시나리오에서 "이어져 있지 않다"고 점선으로 보일 화살표의 `tag` 목록.
  - `labels`: 그림 위에 얹을 짧은 글. `{"text": "연결 없음", "col": 1, "row": 1.6}`.

상태는 여덟 가지다. 색과 표시는 재생기가 정하므로 spec에 쓰지 않는다. 색 규칙은 장표와 같다(`diagram-slides` "장표 한 장"의 색 표): 파랑은 지금 도는 곳, 빨강은 문제, 나머지는 회색이고 상태는 글자와 ✓·✕·!·점선으로 가른다. 정상 흐름에는 표의 앞 다섯만 쓰고, 뒤 셋은 실패 시나리오를 그릴 때만 쓴다.

| 상태 | 뜻 | 상자 아래 기본 글자 | 모양 |
| --- | --- | --- | --- |
| `idle` | 아직 차례가 아니다 | (없음) | 회색 |
| `run` | 지금 돌고 있다 | 실행 중 | 파랑, 깜빡임 |
| `wait` | 앞 상자를 기다린다 | 기다리는 중 | 회색 점선 테두리 |
| `ok` | 끝났다 | ✓ 성공 | 회색 |
| `skip` | 돌 필요가 없어 건너뛰었다 | 건너뜀 | 회색 점선, 흐리게 |
| `fail` | 실패했다 | ✕ 실패 | 빨강 채움 |
| `blocked` | 앞이 실패해 돌지 못했다 | 앞이 실패해 멈춤 | 빨강 점선 테두리 |
| `warn` | 끝났지만 결과를 믿을 수 없다 | ! 주의 | 빨강 테두리 |

화살표 모양은 양 끝 상자의 상태로 정해진다. 앞이 `ok`이고 뒤가 `run`이면 흐르는 점선, 둘 다 끝났으면 회색 실선, 실패가 퍼지면 빨간 점선이다.

## 굽기

1. 견본을 저장 폴더에 `NN-<개념>.json`으로 복사해 채운다. 저장 폴더와 이름 규칙은 부른 쪽이 정한다(onboarding이면 `~/onboarding/<주제>/motion/`, 곁가지 질문은 `side-<개념>.json`). 정한 곳이 없으면 작업 폴더의 `motion/`에 둔다.
2. 굽는다. 출력 경로를 생략하면 같은 이름의 `.html`이 생긴다.

   ```bash
   python3 <스킬 폴더>/scripts/render_motion.py <저장 폴더>/NN-<개념>.json
   ```

3. 종료 코드를 본다.

   | 코드 | 뜻 | 할 일 |
   | --- | --- | --- |
   | 0 | HTML을 만들었다. 상자 글자 넘침, 상자를 지나는 화살표, 끝까지 자동 재생되는지를 Chrome으로 검사해 통과했다. 실패 상태가 든 시나리오가 있으면 "확인:" 줄로 알려 준다 | "확인:" 줄이 나오면 그 시나리오가 "정상 흐름이 기본이다"의 넣는 쪽에 드는지 다시 본다. 들지 않으면 빼고 다시 굽는다. 그 뒤 보내기 전 확인으로 간다 |
   | 1 | 굽지 못했다(Chrome 없음, JSON 문법 오류, 재생기 오류) | 메시지대로 고친다 |
   | 2 | spec이 규칙을 어겼다(없는 상자 이름, 모르는 상태, 긴 글, 겹친 상자, 상자를 지나는 화살표, 채우지 않은 자리). HTML을 만들지 않고, 예전에 구운 HTML이 있으면 지운다 | spec을 고쳐 다시 굽는다. 긴 자막은 줄이고, 단계가 많으면 시나리오를 나눈다 |

4. 기록해 두는 곳이 있으면(예: onboarding의 `deck-spec.md`) HTML 경로를 적는다.

`python3 <스킬 폴더>/scripts/render_motion.py --check`는 견본을 구워 설치를 확인한다.

## 보내기 전 확인

- 검사는 모양만 본다. 단계마다 상태와 자막이 사실과 맞는지는 spec을 근거(코드·문서)와 대조해 확인한다. 특히 "무엇이 끝나야 다음이 출발하나"는 `depends_on`·`run_if` 같은 실제 설정을 읽고 정한다. 실패 시나리오를 넣었다면 "어디까지 멈추나"도 같은 설정으로 확인한다.
- 실패·정지 시나리오가 있으면 넣은 까닭을 한 줄로 댈 수 있는지 본다. 자료의 이슈 절을 옮겼을 뿐이면 뺀다("정상 흐름이 기본이다").
- 특정 단계의 모습을 보려면 주소 끝에 `#시나리오-단계`를 붙여 연다(`…/NN-개념.html#2-4`). headless Chrome으로 스크린샷을 찍어 확인할 수 있다.
- 용어 표기는 장표와 같다(`diagram-slides` "표기"). 기술 용어는 영어 그대로, 문장은 한국어로 쓴다.

## 보내기

- Artifact를 올릴 수 있는 도구(Claude 데스크톱 앱 등)면 구운 HTML을 Artifact로 올리고 링크를 준다. 올릴 수 없으면 파일 경로를 알려 주고 브라우저로 열라고 한다.
- 채팅에는 시나리오마다 결론 한 줄을 쓴다. 요약 장표가 있으면 함께 보낸다.
- 틀린 곳이 드러나면 spec을 고쳐 다시 굽고, 같은 경로로 다시 올린다.

## 맡기기

spec의 상자·화살표·단계별 상태·자막은 사실 관계라서 맡기는 쪽이 정한다. 정한 내용을 JSON으로 옮기고 굽는 일은 가벼운 모델의 서브에이전트에게 맡겨도 된다. 지시문에는 이 문서의 "spec 쓰기"와 "굽기"를 읽으라고 적고, 코드 2가 나오면 무엇을 바꿨는지 보고하게 한다. 한 번 만든 모션그래픽을 고칠 때는 직접 한다.
