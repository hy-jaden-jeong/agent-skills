# golden master

이미 돌아가는 것을 바꾸는 일에서 "기존 출력이 그대로 나온다"를 증명하는 법이다. 바꾸기 전 출력을 기준(golden master)으로 저장해 두고, 바꾼 뒤 같은 입력으로 다시 만들어 견준다. 견본이나 test 몇 개로는 이미 쓰는 사람의 결과물이 그대로인지 알 수 없다.

- 이 확인이 증명하는 것은 "바뀌지 않았다"뿐이다. 새 동작이 맞는지, 옛 출력이 옳았는지는 증명하지 않는다. 그것은 동작마다의 증명이 맡는다.

## 기준 만들기 (첫 slice 전)

1. 대상을 정한다. 이미 만든 결과물 전부다(예: 기존 장표 전부, 기존 API 응답, 기존 report). 견본만으로는 부족하다. 대상과 그 수를 spec의 "회귀 기준"에 적고 slice와 함께 동의받는다.
2. 바꾸기 전 코드로 굽는다. working tree가 깨끗하면 `git worktree add <임시 폴더> <기준 commit>`으로, 아니면 바꾸기 전 폴더를 통째로 사본으로 떠서 그 사본으로 굽는다. 바꾸는 중인 코드로 기준을 구우면 기준이 오염된다.
3. 기준을 두 번 구워 서로 같은지 먼저 본다. 다르면(시각, 난수, 순서) 그 부분을 고정하거나 견줄 대상에서 빼고, 뺐다고 spec에 적는다. 그대로 두면 매번 달라 아무것도 잡지 못한다.
4. 기준에서 이미 실패하는 대상(옛 형식 등)도 그대로 둔다. 바꾼 뒤에도 같은 코드로 실패해야 같은 것이다.

## 견주기 (slice마다, 검증 때 한 번 더)

- 종료 코드는 전부 견준다. 출력 바이트는 기준과 지금이 모두 성공(코드 0)인 대상만 견준다.
- 기준에 없던 대상, 기준에만 있는 대상도 알린다.
- 하나라도 다르면 견주는 script가 0이 아닌 코드로 끝난다. 사람이 결과 글을 읽어야만 알 수 있으면 놓친다.
- 다른 것이 의도한 차이면 직접 열어 보고, 어느 동작(B 번호) 때문인지 spec에 적은 뒤 그 대상만 기준을 갱신한다. 의도하지 않은 차이면 그 slice는 끝나지 않았다.
- 결과 수("기준 N개 중 코드 0인 M개, 종료 코드 다름 0, 바이트 다름 0")를 slice 표의 증명 칸과 동작 표의 증명 칸에 적는다.

## 두는 곳

- 굽는 script와 견주는 script는 spec 옆(예: `<spec 이름>-tests/regress/`)에 둔다. 다시 굽는 명령을 spec의 "회귀 기준"에 적는다.
- 기준 출력은 commit하지 않는다. 기준 commit과 굽는 명령만 있으면 다시 만들 수 있다.
- 오래 걸리면(수 분 이상) background로 돌리고, 기다리는 동안 다음 slice의 test를 쓴다. 단 다음 slice의 코드 변경이 돌고 있는 굽기에 섞이지 않게, 견줄 상태를 사본으로 떠서 굽는다.
